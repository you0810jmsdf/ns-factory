## 2026-08-24 — レシート取込: 突合の誤マッチ防止（店名なし照合の廃止・「要確認」の新設）

- 対象: `kanri-room/receipt-intake/index.html`
- 発端: 「毎月MFからCSVを出して突合すると重複しないのか」という問い。**重複防止は機能していた**
  （台帳の `mf_status` が永続フラグ、CSV出力対象は「未登録」のみ、MF側は `used` で1対1）が、
  調べる過程で**逆方向の事故＝計上漏れ**の穴が2つ見つかった。
- ⛔ **店名を見ない照合を復活させないこと。** 按分後7,140円のガソリンが無関係な7,140円のコンビニと
  一致した（実測）。誤って「MF登録済」になると、その経費は二度とCSVに出ず永久に計上されない。
- ⛔ **`storeMatch()` の `'unknown'` を `'yes'` に丸めないこと。** MFの摘要が空のとき、
  金額と日付だけで別取引と一致してしまう。`'unknown'` は「要確認」として人の判断に回す。
- 照合の順序: 金額（税込 or 按分後）と日付±3日で**候補を集め**、店名で確定させる。
  店名一致が1件でもあればそれを採る（摘要が空の候補より優先）。
- 「要確認」は `markMatchedBtn` の一括更新に**含めない**。安全側に倒すのが仕様。
- 検証: ロジック単体（6ケース）＋本番Playwright。摘要空→要確認・ダイアログ出ない／
  店名あり→一致・ダイアログ1件／按分後×別店舗→MF未登録。実台帳はキャンセルして変更していない。
- 既知の課題: PC側 `監理部\export_tax_csv.py` の `reconcile()` は金額＋日付±60日のみで**店名を見ない**。
  画面版より緩い。正となるのは画面側の `mf_status`（手順書に明記済み）。

## 2026-08-24 — 書類番号を「保存時に採番」へ変更（開くだけで番号が飛ぶ問題）

- 対象: `invoice/editor.html` / `invoice/js/editor.js`（GAS `Nsfactory-Billing/Documents.gs` も同日更新・@10）
- 症状: 書類番号が飛ぶ（I-2026-009 → 012 → 021 → 022 → 031）。事業主が「番号が合っていない」と気付いた。
- 原因: `Numbering.gs` の `getNextNumber` は **ScriptProperties のカウンタを +1 して保存する**。
  これを editor.js が **画面読み込み時**に呼んでいたため、保存せず閉じただけで番号を消費していた。
- 対策: 採番を **`createDocument` が台帳へ行を書く直前**に移した。
  `doc.number` が空のときだけサーバが採番し、番号が渡ってきた場合は尊重する
  （旧版フロント・`promoteDocument`・`submitQuoteRequest` と互換）。
- ⛔ **editor.js から `API.getNextNumber` を呼び戻さないこと。** 画面を開くたびに番号が飛ぶ。
  新規時は番号欄を空にして `showPendingNumber()` を出し、保存後に `res.number` を反映する。
- ⛔ **新規保存が通ったら `editId` を必ず立てること。** `editId` は `let`。
  立て忘れると2回目の「保存」で `createDocument` が再び走り、**別番号の書類が増える**
  （旧実装では同番号の行が2本できていた。どちらも台帳が壊れる）。
- 反映順は **GAS → フロント**。逆にすると番号なしの行が台帳に書かれる。
- 未保存のまま印刷しようとすると確認ダイアログ。印刷面の番号欄は「（保存後に採番）」と出る。
- 検証: API で基準値を確定（I-2026-033）→ 新規作成画面を**4回**開く → 画面から保存 → **I-2026-034**
  （＝開いても消費しない）。続けて再保存しても I-2026-034 のまま・I-2026-035 は作られない。
  検証用の書類とダミー顧客は削除済（残存0件）。
- ⚠ 残る課題: **`createDocument` は冪等化されていない。** 応答だけ失われて押し直すと別番号で2件できる。
  塞ぐなら `requestId` 方式（`Apps Script/product_register.js` と同作法）。

## 2026-08-21 — 監理幕僚室に暗号資産 計算書ツールを新設

- 対象: `kanri-room/crypto-calc/index.html`（新設）/ `kanri-room/crypto-calc/crypto_calc.zip`（新設）/ `kanri-room/index.html`
- 目的: 国税庁「暗号資産の計算書（総平均法用）」の手計算をやめる。取引所CSVから自動計算する。
- 構成: HTML版（ブラウザ完結・日常の確認用）＋ Python版ZIP（提出用xlsx生成が必要なとき）。
  ロジックは同一で、HTML版は起動時にセルフテストを走らせて両者の一致を自己検証する。
- 対応取引所: メルコイン（月次CSV）/ GMOコイン（年間取引報告書CSV・**BOM付き**）/ OKJ（PDFのみのため手入力JSON）。
- ⛔ **JavaScript の Number で金額計算をしないこと。** 暗号資産の数量（小数8桁以上）と円建て金額の積で
  桁落ちし、総平均法は割り算を含むため誤差が年末残高に蓄積する。**BigInt の固定小数点（小数20桁）**で実装してある。
  `fmt()` は切り捨てではなく**四捨五入**にすること（切り捨てだと 3.475553315 が 3.475553314999… となり、
  繰越残高として翌年へ渡したときに誤差が残る）。
- ⛔ **総平均法は「通貨ごと」に全取引所を合算すること。** 取引所ごとに別々の計算書を作ると
  同じBTCに総平均単価が複数生まれて所得金額が変わる。国税庁様式が「暗号資産の名称」1件に対して
  「取引所の名称」を複数行持つ構造なのはこのため。
- GMOコインCSVの読み方（実測に基づく）:
  - 現物は精算区分 `販売所取引` / `取引所現物取引`。売却価額は**手数料差引後の「日本円受渡金額」**を採る
    （約定金額を使うと国税庁様式の値とずれる）。
  - 証拠金取引の損益 = `暗号資産FX取引` かつ取引区分 `決済` の受渡金額 ＋ `暗号資産FXレバレッジ手数料` の受渡金額。
    **新規建玉の行は損益ゼロなので集計しない。**
  - **年間取引報告書に翌年1月1日の行が混ざる。** 対象年以外は必ず除外すること（実測で3行混入していた）。
- プライバシー: 読み込んだCSVは**一切送信しない**（fetch/XHR なし・完全クライアント処理）。
  ZIPは配布前に個人情報・実取引データを除去済（氏名の既定値・docstringの実数値・READMEの運用実績を全て架空値化）。
  `保全部\check_public_leak.py` で危険度「高」ゼロを確認してから push した。
- ⛔ **ZIPを作り直すときは必ず漏洩検査を通すこと。** 初回ビルドで氏名・BTC保有量・
  マンション売却の決済日と金額まで混入していた（push前に検知して破棄）。`__pycache__` の混入にも注意。

  年末残高が完全一致**（合計3,007,656円）／公開URLの HTTP 200 と ZIP 94,667バイトを実測。
