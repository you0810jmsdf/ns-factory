# CBIサイト用「更新履歴＋SNS告知」プロンプト

ns-factory サイトで作った「お知らせ欄への掲載＋SNS告知」を CBI サイトにも作るための、
別セッションへ渡すプロンプト。以下をそのままコピーして使う。

---

## 前提（渡す前に埋める）

| 項目 | 値 |
| --- | --- |
| CBIサイト | `https://communitybankinzai.github.io/cbi-site/` |
| リポジトリ | `communitybankinzai/cbi-site` |
| SNS告知先 | **（未定：Threads / X / Facebook / なし）** |
| GASプロジェクト | **（未定：既存 `Nsfactory-SNS-AutoPost` に同居 / CBI専用を新規作成）** |
| 候補の出どころ | **（未定：ns-factory は業務日誌。CBI に相当するものがあるか）** |
| 承認メールの宛先 | **（未定）** |

未定のままでも着手はできる。§0 で先に確定させること。

---

## プロンプト本文（ここから下をコピー）

````
CBIサイト（communitybankinzai/cbi-site、https://communitybankinzai.github.io/cbi-site/）に、
サイトの更新履歴を「承認したものだけ」掲載し、あわせてSNSでも告知できる仕組みを作ってほしい。

ns-factory サイト（you0810jmsdf/ns-factory）で同じものを一度作り切ってあるので、
その設計をなぞる。実装と、そこで踏んだ落とし穴は
`you0810jmsdf/ns-factory` の `docs/news-publish-setup.md` と `CLAUDE.md`
（2026-08-05〜08-06 の項）に全部書いてある。**着手前に必ず両方読むこと。**

## 事業主について（設計判断に直結する）

- **PCをほとんど使わない。** 承認操作はスマホだけで完結しなければ運用に乗らない。
- ns-factory では最初「メールのボタンを押す」方式で作ったが、
  スマホのブラウザで Google 認証が通らず**最後まで押せなかった**。
  デプロイ設定（実行:自分／アクセス:全員）を正しくしても、URLがメールと完全一致していても、
  Drive の「現在、ファイルを開くことができません」で止まり続けた。
  → **メール返信方式に切り替えて解決した。CBIでも最初から返信方式で作ること。**

## 作るもの

### 1. サイト側（cbi-site リポジトリ）

- 更新履歴データを持つ JSON（ns-factory では `news-data.json`）
- それを読んで描画するコード
- 追記スクリプト（ns-factory では `tools/add_news.js`）
- `repository_dispatch` で受ける GitHub Actions ワークフロー

### 2. GAS側

- 候補メールの送信（返信の書き方を本文に明記する）
- 10分おきに返信を拾って処理するトリガー関数
- SNS告知の関数

## 承認のしかた（ns-factory と同じにする）

候補メールに**返信**して、1行目に次のいずれかを書く。

| 1行目 | 動作 |
| --- | --- |
| 掲載 | サイトの更新履歴に載せる |
| 告知 | サイトに載せる ＋ SNSにも投稿する |
| 不要 | 載せない |
| `掲載 2026年8月 — 直した本文` | 文面を差し替えて掲載 |

- 引用部分は読まない（引用の中の「掲載」で誤爆させない）
- コマンド以外の返信は何もしない
- 処理済みは Gmail ラベルで判定する
- **どのコマンドでも必ず結果を返信する**（返信が来ないと動いたか分からない）
- **コマンド一覧は候補メールの本文に必ず書く。** 別の場所に書いても覚えられない

## 必ず守ること（ns-factory で実際に事故った点）

1. **冪等にする。** GASは処理が完了しても応答だけ失われて再送されることがある。
   追記スクリプトは「同じidがあれば何もせず exit 0」にする。
   ns-factory では重複チェックが無くて更新履歴が二重に載った。

2. **表示は「置き換え」ではなく「足し込み」にする。**
   書き込み経路が複数になったとき、置き換えだと片方の書き込みが表示から消える。
   ns-factory ではこれで一度壊した。同じ本文は表示時に1件へ畳むこと。

3. **年をコードにベタ書きしない。**
   ns-factory の GAS は `'<span>2026年のお知らせ</span>'` を挿入位置の目印にしており、
   2027年になると別の年のグループに入ってしまう。年グループの生成・並べ替えは
   リポジトリ側のスクリプトに持たせること。

4. **SNS告知の呼び出しは必ず try/catch で囲む。**
   告知の失敗で掲載処理まで落とすと、サイトには反映済みなのに画面はエラーになり、
   押し直しで二重掲載を招く。失敗はログに残して掲載は成功として完了させる。

5. **投稿の頻度ガードを告知に適用しない。**
   ns-factory の Threads 投稿には「投稿間隔ガード」「時間帯別の本数上限」があり、
   定期投稿の直後に手動告知を出そうとすると弾かれた。
   停止スイッチ（KillSwitch）だけ尊重し、頻度ガードは通さない専用の呼び口を用意すること。
   ただし成否の記録は通常投稿と同じに残す（連続失敗の自動停止と月次集計に乗せるため）。

6. **PATはリポジトリごとに必要。**
   ns-factory の `GITHUB_PAT_NS_FACTORY` は ns-factory 限定スコープなので **CBIには使えない。**
   `communitybankinzai/cbi-site` に対する Fine-grained PAT（Contents: Read and write）を
   別途作り、スクリプトプロパティに登録する。`dispatches` もこの権限で通る。

7. **受け取った値は workflow の `env:` 経由でのみ渡す。**
   `run:` に `${{ }}` を直接展開しない。

8. **本文はHTMLとして流し込まない。** textContent で入れる。
   リンクを許すなら href を検査して `javascript:` 等を弾く。

## 最初に確認すること（§0）

以下が未確定なので、着手前に事業主に確認する。

1. **SNS告知先はどこか**（Threads / X / Facebook / 当面なし）。
   CBI は市民活動団体なので、ns-factory の Threads アカウントとは分けるはず。
   アカウントとアクセストークンの有無を確認する。
2. **GASプロジェクトは既存に同居させるか、CBI専用を新規に作るか。**
   ns-factory の `Nsfactory-SNS-AutoPost` に同居させると設定が混ざる。
   団体の活動と個人事業を分ける意味でも、**CBI専用を新規作成するのが妥当**だと思うが、
   運用者が同一人物なので管理を一箇所に寄せたい可能性もある。確認すること。
3. **更新履歴の候補は何から作るか。**
   ns-factory は業務日誌から日次で自動検知していた。CBI に相当する記録があるか。
   無ければ「手動で1行書いて送る」入口から始めるほうが早い。
4. **承認メールの宛先。**
5. **cbi-site の現状。** 更新履歴セクションが既にあるか、どんなマークアップか。
   まずリポジトリを読んで把握すること。

## 進め方

1. §0 を確認する。答えが出るまで、リポジトリ側（サイト表示・JSON・Actions）だけ先に進めてよい。
   GAS は SNS の答えが出てから。
2. リポジトリ側ができたら、Actions の手動実行だけで通しテストする（GASを触る前に検証できる）。
3. GAS 側を入れ、実際に候補メールへ返信して通しで確認する。
4. 変更内容と落とし穴は cbi-site 側の作業記録に残す。

## やらないこと

- ns-factory リポジトリには手を入れない。参照のみ。
- メールのボタン方式を主経路にしない（スマホで通らない実績がある）。
  PC用の補助として残すのは可。
````
