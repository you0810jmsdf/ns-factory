CASE 01 ／ 販売幕僚

広告成果の3段階分解

要点広告は3段階に分けて直す

広告や商品ページの成果は「見られた回数×クリックされた割合×購入された割合」の掛け算で決まる、という考え方。どこで数字が落ちているかを3段階に分けて見れば、直す場所がすぐ分かる。

現状分析EC改善知見はあるが集計なし

  • Creemaなど複数チャネルで販売しているが、閲覧→クリック→購入を段階別に集計する仕組みはまだない
  • 商品ページ構成（結論→体験→弱点→おすすめ）やボタン文言の改善知見は蓄積済み
  • オーダーメイドは見積PDF送付からお礼メールまで手作業フローで、進捗は公開ページで管理している

図解

閲覧数を数える → クリック率(CTR)を計算 → 購入率(CVR)を計算 → 低い段階を優先して改善

提言Creemaの閲覧→購入を3段階で集計

  1. Creemaの商品ページ閲覧数・クリック数・購入数を今月分集計する
  2. CTRが低い商品は画像やタイトルを見直す
  3. CVRが低い商品はページ構成（結論→体験→弱点→おすすめ）を見直す
  4. 効果が確認できたらminneなど他チャネルにも3段階集計を広げる
いま閲覧数と購入数しか見ておらず、どこで離脱しているか分からない
→
実行後表示→クリック→購入の3段階で数字を見て改善点を絞れる

CASE 02 ／ 販売幕僚

アフィリエイト目標逆算と型選び

要点アフィリエイトの目標から商品選び

アフィリエイト（紹介して売れたら報酬がもらえる仕組み）は月1万円稼ぐなら安い商品だと大量に売る必要がある。1万〜5万円の商品を軸にし、最初は得意分野を絞った「カテゴリ特化型」サイトが書きやすいという記事。

現状分析アフィリエイト注意点のみ明記

  • 型紙PDFの注意点に「アフィリエイトや外部リンク利用時は表示・表記を確認する」と記載済み
  • 材料ガイドは購入先・価格・在庫が変動する前提で書く方針になっている
  • 1万〜［数値］帯の工具・革を紹介する仕組みは社内資料にまだ見当たらない

図解

月の目標報酬を決める → 必要な売上個数を逆算 → 1万〜5万円帯の商品を選ぶ → カテゴリ特化型サイトを作る

提言工具・革の紹介リストを作る

  1. 1万〜5万円帯のレザー工具・革をリスト化し紹介候補にする
  2. まずはカテゴリ特化型で書きやすいテーマを選んでみる
  3. Amazon提携は記事数を増やしてから申し込む順序を守る
  4. 型紙PDFの表示・表記ルールを確認してから掲載する
いま紹介する商品の価格帯やサイト型が未整理
→
実行後1万〜［数値］帯の商品リストと型が決まる

CASE 03 ／ デジタル幕僚

Claude切替時の引き継ぎ書でコスト削減

要点AIの引き継ぎ書でコスト激減

長いAI作業の途中で安いAI（Sonnet）から賢いAI（Opus）に切り替えるとき、作業内容を丸ごと読み直すと料金が高くつきます。先に「目的・触ったファイル・失敗点・次の一手」を短くまとめた引き継ぎ書を書いてから切り替えると、費用を大きく減らせるという工夫です。

現状分析引き継ぎ書はあるが切替専用なし

  • AI共通ブリーフ.mdやデジタル幕僚_引き継ぎ書.mdなど、セッションの引き継ぎ文書はすでに運用している
  • GMOコイン自動売買などClaude・Geminiを使う長時間作業があり、モデル切替時のコスト整理はまだ未着手
  • モデル切替専用のテンプレートや手順書としては整備されていない

提言引き継ぎ書テンプレートで切替コストを抑える

  1. 現行の引き継ぎ書に「目的・触ったファイル・失敗点・次の一手」の項目を追加する
  2. Sonnet→Opus切替前に2万トークン以内のHANDOFF.mdを書く手順書を作る
  3. GMOコイン自動売買など長時間セッションで試験導入し効果を確認する
  4. 効果が見えたらAI共通ブリーフ運用全体に展開するか検討する
いまモデル切替のたびにセッション全体を読み直しコスト増
→
実行後引き継ぎ書だけ読んで再開し、切替コストを抑えられる

CASE 04 ／ デジタル幕僚

Opus＋軽量AI分業での高速化

要点強いAIと軽いAIを分担で高速化？

X（旧Twitter）で「Opus 5.5という強いAIと、Jevという軽いAIを組み合わせると、Claude単体より200倍速く400倍安くなる」という投稿がありました。ただし具体的な作業内容や品質の裏付けはまだ示されていません。

現状分析すでに軽重分業を一部運用中

  • 問い合わせ対応はHaiku4.5（実務相談・有料枠）とGemini2.5Flash（雑談・無料枠）に役割分担済み
  • 意図判定の仕組み（nsfDetectBusinessIntent）で軽い判定→重い判定へ振り分けている
  • 現時点では問い合わせ・受注メールの仕分けには同様の設計をまだ適用していない

図解

問い合わせ受信 → 軽いAIで意図判定 → 重いAIで実務相談回答 → 軽いAIで雑談対応

提言軽重AI分業をメール仕分けにも広げる

  1. 既存の意図判定ロジックを問い合わせ・受注メール仕分けに転用できないか試設計する
  2. 軽いAIで一次仕分け、重いAIで本回答という2段階構成を小さく試す
  3. 導入後は処理速度・コスト・判定精度を比べて効果を確認する
いま問い合わせメールの仕分けは手動や一括処理が中心
→
実行後軽いAIが先に仕分けし、重いAIが必要な分だけ対応する

CASE 05 ／ デジタル幕僚

Codex Auto-review無料化

要点Codexの自動レビューが無料に

Codexというプログラム作成AIに「操作の安全チェックを別のAIが代わりにやってくれる」機能が無料になりました。危ない操作だけ止めてくれるので、いちいち人が承認ボタンを押さなくても長い作業を任せられるようになります。

現状分析CodexはCLIで一部未完

  • GMOコイン自動売買でCodexをCLI 0.153.4で使用、Windowsの制約で一部未完のまま
  • 管理画面のボタンからCodexを動かす構想があり、定型作業の自動起動を検討中
  • 現状は対話形式でCodexに都度作業を依頼する運用になっている

図解

before

  • Windowsの制約でCodex実装が未

after

  • Auto-reviewで安全な操作は自動

提言Codexの委譲ルールを見直し無料レビューを試す

  1. Codexの現行委譲ルールを確認し、Auto-reviewをONにして試す
  2. GMOコイン自動売買のCodex実装を、この機能を使って再検証する
  3. 管理画面のボタンからCodexを動かす構想と組み合わせ、定型作業の自動化を検討する
  4. 夜間に無人で動かす処理での承認待ち解消を試す
いまCodexは操作のたびに承認ボタンを押す必要がある
→
実行後危険な操作だけ審査され、安全な作業は自動で進む
